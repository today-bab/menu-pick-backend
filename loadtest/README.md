# 부하 테스트

메뉴 뽑기 API(`GET /api/menus/pick`)에서 **공유 캐시(Valkey)가 응답 시간과 카카오 호출 수를 얼마나 줄이는지** 잰다.
운영(k8s)과 같은 구성을 로컬 Docker로 띄우고, 카카오만 가짜 서버(WireMock)로 바꿔 실제 API 한도를 쓰지 않는다.

```
k6 ─▶ backend-1 ─┐
  └─▶ backend-2 ─┼─▶ valkey (공유 캐시, 운영과 같은 설정)
                 └─▶ kakao (WireMock: 페이지당 15곳, 응답 지연 150ms, 3페이지에서 끝)
```

## 실행

```sh
./loadtest/run.sh                 # 시나리오 4개 (약 3분)
./loadtest/run.sh hit miss        # 고른 시나리오만
RATE=50 DURATION=60s ./loadtest/run.sh
```

- Docker와 python3가 필요하다. k6는 컨테이너로 돌리므로 설치하지 않아도 된다.
- 백엔드 이미지는 저장소의 `Dockerfile`로 빌드한다 (운영과 같은 이미지).
- 시나리오마다 Valkey를 비우고 WireMock 요청 기록을 지운 뒤 실행한다. 결과 원본은 `loadtest/results/`(git 제외)에 남는다.
- 결과에 넣지 않는 15초 예열을 먼저 한다 (JVM이 처음 몇 초 느림).

| 시나리오   | 요청                                               | 보려는 것                              |
| ---------- | -------------------------------------------------- | -------------------------------------- |
| `hit`      | 같은 칸을 초당 30번, 30초                          | 캐시 적중 시 응답 시간                 |
| `miss`     | 매번 다른 칸을 초당 30번, 30초                     | 캐시가 없을 때 (매 요청 카카오 3번)    |
| `shared`   | 칸 20개를 두 백엔드에 번갈아 초당 30번, 30초       | 두 인스턴스가 캐시를 함께 쓰는지       |
| `stampede` | 비어 있는 한 칸에 50개를 동시에                    | 같은 칸 동시 요청 시 중복 호출         |

## 결과 (2026-10-25)

Apple M4 Pro, Docker Desktop (12 CPU, 메모리 7.7GB). 같은 Mac에서 k6·백엔드·카카오가 함께 돌기 때문에
절댓값보다 **시나리오 사이의 차이**를 보는 용도다.

| 시나리오 | 요청 수 | 실패율 | 중앙값 | p95 | p99 | 카카오 호출 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| hit | 901 | 0.0% | 5ms | 7ms | 465ms | 42 |
| miss | 901 | 0.0% | 462ms | 467ms | 470ms | 2703 |
| shared | 901 | 0.0% | 3ms | 5ms | 464ms | 60 |
| stampede | 50 | 0.0% | 1122ms | 1288ms | 1290ms | 150 |

### 읽는 법

- **캐시 효과**: p95가 467ms(`miss`)에서 7ms(`hit`)로 줄었다. 카카오 호출은 요청 901건에 2703번(요청마다 3페이지)에서 42번으로 줄었다.
- **공유 캐시**: `shared`는 요청을 두 백엔드에 번갈아 보냈는데도 카카오 호출이 정확히 칸 20개 × 3페이지 = 60번이다.
  인스턴스마다 캐시를 따로 가졌다면 최대 120번이 된다.
- **남은 문제, 같은 칸 동시 요청**: 캐시가 비어 있는 동안 같은 칸에 들어온 요청은 모두 카카오를 부른다.
  - `stampede`는 50개 요청이 전부 카카오를 불러 150번 호출됐다. 이상적이면 3번이다.
  - `hit`의 42번도 같은 이유다. 첫 응답이 오기 전 약 0.46초 동안 들어온 14개 요청이 모두 미스가 났다 (14 × 3).
  - p99가 460ms대인 것도 이 첫 미스들 때문이다.
  - 동시 요청이 몰리면 카카오 호출이 한꺼번에 늘어 응답도 느려진다 (`stampede` 중앙값 1.1초).

# 부하 테스트

메뉴 뽑기 API(`GET /api/menus/pick`)에서 **공유 캐시(Valkey)가 응답 시간과 카카오 호출 수를 얼마나 줄이는지** 잰다.
운영(k8s)과 같은 구성을 로컬 Docker로 띄우고, 카카오만 가짜 서버(WireMock)로 바꿔 실제 API 한도를 쓰지 않는다.

```
k6 ─▶ backend-1 ─┐
  └─▶ backend-2 ─┼─▶ valkey (공유 캐시, 운영과 같은 설정)
                 └─▶ kakao (WireMock: 페이지당 15곳, 응답 지연 150ms, 3페이지에서 끝, 비동기 응답)
```

백엔드는 반경 1km를 3×3 구역으로 나눠 구역마다 검색하므로 캐시 미스 한 번에 카카오를 27번(9구역 × 3페이지) 부른다.
가짜 서버가 먼저 병목이 되지 않도록 WireMock은 응답 지연 동안 스레드를 붙잡지 않는 비동기 응답으로 띄운다.

## 실행

```sh
./loadtest/run.sh                 # 시나리오 4개 (약 5분)
./loadtest/run.sh hit miss        # 고른 시나리오만
RATE=50 DURATION=60s ./loadtest/run.sh
```

- Docker와 python3가 필요하다. k6는 컨테이너로 돌리므로 설치하지 않아도 된다.
- 백엔드 이미지는 저장소의 `Dockerfile`로 빌드한다 (운영과 같은 이미지).
- 시나리오마다 Valkey를 비우고 WireMock 요청 기록을 지운 뒤 실행한다. 결과 원본은 `loadtest/results/`(git 제외)에 남는다.
- 결과에 넣지 않는 15초 예열을 먼저 한다 (JVM이 처음 몇 초 느림).

| 시나리오   | 요청                                               | 보려는 것                              |
| ---------- | -------------------------------------------------- | -------------------------------------- |
| `hit`      | 같은 칸을 초당 30번, 30초                          | 캐시 적중 시 응답 시간                 |
| `miss`     | 매번 다른 칸을 초당 30번, 30초                     | 캐시가 없을 때 (매 요청 카카오 27번)   |
| `shared`   | 칸 20개를 두 백엔드에 번갈아 초당 30번, 30초       | 두 인스턴스가 캐시를 함께 쓰는지       |
| `stampede` | 비어 있는 한 칸에 50개를 동시에                    | 같은 칸 동시 요청 시 중복 호출         |

## 결과

Apple M4 Pro, Docker Desktop (12 CPU, 메모리 7.7GB). 같은 Mac에서 k6·백엔드·카카오가 함께 돌기 때문에
절댓값보다 **시나리오 사이의 차이**를 보는 용도다.

### 읽는 법

- **캐시 효과**: p95가 472ms(`miss`)에서 8ms(`hit`)로 줄었다. 카카오 호출은 요청 900건에 24327번(요청마다 27번)에서 27번(칸 하나를 한 번)으로 줄었다.
- **캐시 채우기 락**: 같은 칸 동시 요청 50개(`stampede`)의 카카오 호출이 1350번에서 27번으로, p95가 1634ms에서 490ms로 줄었다.
  - 카카오 호출이 한꺼번에 몰리지 않아, 기다린 요청도 첫 조회와 거의 같은 시간에 응답한다.
  - `hit`의 첫 0.46초 동안 몰린 미스도 한 번만 조회해 405번이 27번이 됐고, p99가 467ms에서 213ms로 줄었다.
  - 락을 잡은 쪽이 실패하면 기다리던 쪽이 이어받고, 3초가 넘거나 Valkey에 문제가 있으면 기다리지 않고 직접 조회한다.
- **공유 캐시**: `shared`는 요청을 두 백엔드에 번갈아 보냈는데도 카카오 호출이 정확히 칸 20개 × 27번 = 540번이다.
  인스턴스마다 캐시를 따로 가졌다면 최대 1080번이 된다.
- **구역 검색의 비용**: 9구역을 동시에 부르므로 캐시 미스 응답 시간(중앙값 462ms)은 그대로지만, 카카오 호출은 9배가 됐다.
- **찾아서 고친 문제, HTTP/2 동시 스트림 한도**: 구역 검색을 처음 붙였을 때 `stampede`에서 64%가 실패했다.
  - JDK HttpClient가 HTTP/2 연결 하나에 요청 50 × 9구역을 몰아 보내다 서버의 동시 스트림 한도를 넘었다 (`too many concurrent streams`).
  - 카카오 호출을 HTTP/1.1로 고정해 필요한 만큼 연결을 늘리게 하자 실패가 0%가 됐다.
- **락 전의 문제, 같은 칸 동시 요청** (위 락 결과로 해결): 캐시가 비어 있는 동안 같은 칸에 들어온 요청은 모두 카카오를 불렀다.
  - `stampede`는 50개 요청이 전부 카카오를 불러 1350번 호출됐다. 이상적이면 27번이다.
  - `hit`의 405번도 같은 이유다. 첫 응답이 오기 전 약 0.46초 동안 들어온 15개 요청이 모두 미스가 났다 (15 × 27).
  - 구역 검색으로 호출 수가 9배가 되면서 이 중복도 9배로 커졌다.

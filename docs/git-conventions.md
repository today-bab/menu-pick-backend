# Git 작업 규칙

모든 작업은 **이슈 → 브랜치 → PR → merge 커밋** 순서로 `main`에 붙인다. `main`에 직접 push하지 않는다.

## 1. 이슈 만들기

- 작업을 시작하기 전에 GitHub 이슈를 먼저 만든다.
- 이슈 하나는 브랜치 하나, PR 하나로 끝낼 수 있는 크기로 잡는다. 크면 이슈를 나눈다.

## 2. 브랜치 만들기

`main` 최신 상태에서 이슈 번호를 넣어 브랜치를 만든다.

```sh
git switch main
git pull
git switch -c feat/12-include-menu-param
```

형식: `<타입>/<이슈번호>-<짧은-설명>` (영어 소문자, 단어는 `-`로 연결)

| 타입    | 용도                          |
| ------- | ----------------------------- |
| `feat`  | 기능 추가·변경                |
| `fix`   | 버그 수정                     |
| `refactor` | 동작 변화 없는 구조 개선   |
| `test`  | 테스트만 추가·수정            |
| `docs`  | 문서                          |
| `chore` | 설정, 의존성 등 기타          |
| `ci`    | CI 워크플로                   |
| `build` | 빌드 설정(Gradle, Dockerfile) |

## 3. 커밋

형식: `<타입>: <한국어 요약>` — 타입은 브랜치 타입과 같은 목록을 쓴다.

```
feat: 뽑기 API에서 다시 넣을 메뉴(includeMenu) 파라미터 받기
fix: 배포 중 502를 막도록 종료 전 대기 추가
```

- 커밋 하나는 하나의 책임만 담는다. 한 브랜치에 작은 커밋 여러 개가 쌓여도 괜찮다.
- 요약은 무엇을 왜 바꿨는지 드러나게 쓰고, 마침표를 붙이지 않는다.

## 4. PR 열기

- 제목은 커밋 메시지와 같은 형식으로 쓴다.
- 본문에 `Closes #<이슈번호>`를 넣어 머지 시 이슈가 자동으로 닫히게 한다.
- CI(`./gradlew test`)가 통과해야 머지한다.

## 5. 머지

- **Create a merge commit**으로 머지한다. squash·rebase 머지는 쓰지 않는다.
  브랜치의 커밋 이력을 그대로 남기고, 기능 단위로 되돌릴 때 `git revert -m 1 <merge 커밋>`을 쓰기 위해서다.
- 머지 후 브랜치는 삭제한다.
- `main`에 머지되면 CI가 이미지를 빌드하고 `menu-pick-gitops`의 이미지 태그를 갱신해 배포된다.

## 브랜치가 오래 걸릴 때

`main`이 앞서 나가면 브랜치에 `main`을 merge해서 충돌을 미리 해결한다.

```sh
git switch feat/12-include-menu-param
git merge main
```
